# 작업 프롬프트 — 라즈베리파이 드론 연동 환경 세팅 (2026-09-21, 개정 2)

> 라즈베리파이에서 돌아가는 AI 에이전트에게 그대로 붙여 넣는 용도.
> 같이 내릴 명령은 `작업명령_라즈베리파이세팅_260921.md`에 따로 있다.

---

## 배경

이 라즈베리파이에는 **Go1 로봇 연결 세팅이 이미 들어 있고 실로봇 검증까지 끝난 상태**다. 여기에 X500 v2 쿼드콥터 연결을 **추가**한다. 기존 것을 바꾸는 작업이 아니다.

드론 쪽 구성:
- 비행 컨트롤러: 코아 FC H743, PX4
- 배선: FC TELEM1 ↔ 라즈베리파이 GPIO UART (TELEM2에는 무선 텔레메트리 Air Unit이 붙어 있다. 건드리지 않는다)
  - FC TX → 10번 핀 (GPIO15, RXD)
  - FC RX → 8번 핀 (GPIO14, TXD)
  - GND → 6번 핀
- FC 파라미터는 사람이 QGroundControl에서 설정한다: `MAV_0_CONFIG = TELEM1`, `MAV_0_MODE = Onboard`, `SER_TEL1_BAUD = 921600`, `UXRCE_DDS_CFG = 0`. TELEM2(Air Unit) 쪽 `MAV_1_*`, `SER_TEL2_BAUD`는 현재 값 유지

최종 목표는 가시화 웹에서 드론에 제어 명령을 내리는 것. 경로는 웹 → 서버 → MQTT → 라즈베리파이 → MAVLink → FC. 이번 작업 범위는 **라즈베리파이 쪽 환경을 갖추고, 전원만 켜면 드론 연결 준비가 자동으로 되게 만드는 데까지**다. MQTT 규약에 맞춘 드론 브리지는 다음 작업이다.

## 규칙 1 — Go1 세팅 보호 (가장 중요)

**Go1 관련 코드, 설정, 서비스는 읽기만 한다. 수정·삭제·이동·재시작·중지·비활성화 전부 금지.**

- Go1 관련 파일과 디렉터리는 열어 보는 것까지만 허용
- Go1 관련 systemd 서비스, cron, 자동 실행 스크립트에 `stop`, `restart`, `disable`, `mask`, 파일 수정 금지
- Go1이 쓰는 가상환경, 파이썬 패키지, 네트워크 설정(유선 고정 IP 등), MQTT 브로커 설정 변경 금지
- `sudo pip install`처럼 전역 파이썬에 설치하지 않는다. 드론용 패키지는 전부 `~/drone/venv` 안에만
- `apt upgrade`, `apt full-upgrade`, `apt autoremove` 금지. 새 패키지 `apt install`만 허용
- 새로 만드는 것은 전부 `~/drone/` 아래에 두고, systemd 유닛 이름은 `drone-` 접두어를 붙인다
- 드론 쪽 식별자는 Go1과 겹치지 않게 한다: device_id는 `x500-001`, MQTT clientId도 별도. **clientId가 같으면 서로 연결을 끊는다**
- 포트 충돌 확인: 드론이 쓸 포트(14540, 14550, 5760)를 Go1 쪽이 쓰고 있지 않은지 먼저 본다

시스템 공용 설정(부트 설정, 시리얼 콘솔, 블루투스)은 드론 때문에 바꿔야 한다. 이건 Go1 쪽에 영향이 없는지 0단계에서 확인하고, **바꾸기 전에 사용자 승인을 받는다.**

작업 전후로 Go1 쪽 상태를 기록해 비교한다. 이게 "Go1을 건드리지 않았다"는 증거다.

## 규칙 2 — 드론 안전

1. FC에 arm, takeoff, 모드 변경, 모터 테스트, offboard 명령을 보내지 않는다. 보낼 수 있는 건 heartbeat와 조회 요청(파라미터 읽기, 메시지 스트림 요청)뿐이다.
2. FC 파라미터를 쓰지 않는다. 값이 예정과 다르면 보고만 한다.
3. 제어용 스크립트는 파일로 만들어 두기만 하고 실행하지 않는다.
4. 자동 실행 대상에 **제어 명령을 보내는 프로그램은 넣지 않는다.** 부팅 시 자동으로 뜨는 건 통신 준비와 상태 확인까지다.

## 규칙 3 — 작업 방식

- 재부팅이 필요하면 바로 하지 않는다. 거기까지 한 일과 재부팅 후 이어서 할 단계를 `~/drone/PROGRESS.md`에 적고, 사용자에게 알린 뒤 확인을 받는다.
- 시스템 설정 파일을 고치기 전에는 `.bak.날짜` 백업을 남긴다.
- 에러가 나면 같은 명령을 반복하지 말고 원인을 먼저 좁힌다.
- 보고는 한국어로 한다.

## 할 일

### 0단계. 현재 상태 파악 (아무것도 바꾸지 않는다)

**0-1. 시스템**
- 모델 `cat /proc/device-tree/model`, OS `cat /etc/os-release`, 아키텍처 `uname -m`, Python 버전
- 부트 설정 파일 위치 (`/boot/firmware/config.txt` 또는 `/boot/config.txt`)와 현재 내용
- 시리얼 장치 `ls -l /dev/serial* /dev/ttyAMA* /dev/ttyS* /dev/ttyACM* /dev/ttyUSB* 2>/dev/null`
- 시리얼 콘솔 사용 여부 `cat /proc/cmdline`
- 블루투스 사용 여부 `systemctl is-enabled hciuart bluetooth 2>/dev/null`

**0-2. Go1 세팅 조사**
- Go1 관련 코드 위치, 가상환경, 설정 파일
- **자동 실행 방식**: `systemctl list-unit-files --state=enabled`, `/etc/systemd/system/`, `~/.config/systemd/user/`, `crontab -l`, `sudo crontab -l`, `/etc/rc.local`, `~/.bashrc`·`~/.profile`, docker/pm2 사용 여부를 확인해 Go1이 부팅 때 어떻게 올라오는지 찾는다
- Go1 연결 방식: 어떤 네트워크 인터페이스(유선/무선)로, 어떤 IP 대역으로 붙는지
- MQTT: 브로커가 이 라즈베리파이에 떠 있는지(`ss -tlnp`로 1883, 9001 확인), Go1 코드가 어느 브로커 주소·토픽·clientId를 쓰는지
- Go1 쪽이 UART(`/dev/serial0`, `ttyAMA0`)나 블루투스를 쓰는지. **쓴다면 즉시 멈추고 보고한다**
- 사용 중인 포트 전체 `ss -tulnp`

**0-3. Tailscale**
- `tailscale status`, `tailscale ip -4`, `systemctl is-enabled tailscaled`
- 지상국 PC가 같은 tailnet에 보이는지와 그 이름·IP
- Go1 때 지상국이 Tailscale로 무엇에 붙었는지(브로커 주소 등)

**0-4. 기준 스냅샷 저장**
`~/drone/baseline/`에 저장한다.
- Go1 관련 서비스들의 `systemctl status` 출력
- `systemctl list-unit-files --state=enabled`
- `ss -tulnp`
- `ip -4 addr`
- `tailscale status`
- Go1 코드 디렉터리의 파일 목록과 해시 (`find ... -type f -exec sha256sum {} +`)

**0단계 보고**: 결과를 표로 정리한다. 특히 ① Go1이 자동 실행되는 방식 ② UART·블루투스 변경이 Go1에 영향을 주는지 ③ 포트 충돌 여부 ④ Tailscale 상태를 분명히 적는다. 1단계에서 바꿀 내용을 제안하고 **승인을 받을 때까지 멈춘다.**

### 1단계. UART 설정 (승인 후)
- 시리얼 로그인 콘솔 끄고 UART 하드웨어 켜기: `sudo raspi-config nonint do_serial_hw 0`, `sudo raspi-config nonint do_serial_cons 1`
- 부트 설정에 `enable_uart=1`
- 모델별
  - Pi 3/4: `dtoverlay=disable-bt`, `sudo systemctl disable hciuart` (0단계에서 블루투스를 Go1이 안 쓴다고 확인된 경우에만)
  - Pi 5: `dtparam=uart0=on`
- 현재 사용자 `dialout` 그룹 추가
- 재부팅 → 규칙 3대로 처리

재부팅 후 확인: `/dev/serial0` 연결 대상, `/proc/cmdline`에서 시리얼 콘솔 제거, **Go1 서비스가 재부팅 전과 똑같이 올라왔는지 기준 스냅샷과 비교**.

### 2단계. 소프트웨어 설치
- apt(새 패키지만): `git python3-venv python3-pip meson ninja-build pkg-config gcc g++`
- `~/drone/venv` 생성 후 `pymavlink`, `mavproxy`, `mavsdk`, `paho-mqtt`
- mavlink-router: `~/drone/src/`에 `--recursive`로 clone, `meson setup build . && ninja -C build && sudo ninja -C build install`
- 설치 도구 버전 기록
- mavlink-router 패키지가 자체 서비스(`mavlink-router.service`)를 설치하면 **활성화하지 않는다.** 자동 실행은 4단계에서 `drone-` 유닛으로 따로 만든다

### 3단계. 수동 연결 확인
`~/drone/scripts/check_link.py` (pymavlink):
- 인자: `--device` (기본 `/dev/serial0`, `udpin:0.0.0.0:14540` 형식도 허용), `--baud` (기본 921600)
- 동작
  1. heartbeat 최대 10초 대기. 받으면 system/component id, autopilot, 기체 타입, arm 상태, custom mode 출력
  2. 5초간 메시지 종류별 개수와 주기(Hz)
  3. ATTITUDE roll/pitch/yaw를 도 단위로 몇 줄
  4. `MAV_0_CONFIG`, `MAV_0_MODE`, `SER_TEL1_BAUD`, `MAV_1_CONFIG`, `MAV_1_MODE`, `SER_TEL2_BAUD`, `UXRCE_DDS_CFG` **읽기만**. 라즈베리파이 연결이 TELEM1 인스턴스인지, Air Unit 인스턴스가 TELEM2에 살아 있는지 같이 판단해 출력
  5. 종료 코드: 연결 성공 0, 실패 1 (4단계 자동 감지에서 재사용)
- 921600에서 안 되면 57600도 시도. 그래도 안 되면 원인 후보 정리: TX/RX 반대, 보드레이트, FC 파라미터 미설정, 시리얼 콘솔 점유, 장치 파일

통과 기준: heartbeat와 ATTITUDE 수신. 기체를 기울였을 때 값이 바뀌는지는 사용자에게 확인을 요청한다.

### 4단계. 부팅 시 자동 연결 준비

**원칙**: Go1이 부팅 때 올라오는 방식(0-2에서 찾은 것)과 **같은 방식**을 쓴다. Go1이 systemd면 systemd로, 다른 방식이면 그 방식에 맞춘다. 아래는 systemd 기준 설계이고, 방식이 다르면 같은 구조로 옮긴다.

**동작 목표**: 라즈베리파이 전원을 켜면
- 드론 FC가 연결돼 있으면 → 드론 통신이 자동으로 준비된다
- Go1이 연결돼 있으면 → 지금처럼 Go1 세팅이 올라온다 (**Go1 쪽 자동 실행은 손대지 않는다.** 원래 하던 대로 둔다)
- 둘 다 없으면 → 드론 쪽은 조용히 대기하면서 주기적으로 다시 확인한다

**구성**

| 유닛 | 역할 |
|---|---|
| `drone-detect.service` | 부팅 후 실행. `/dev/serial0`에서 heartbeat를 찾는다. 찾으면 `drone.target`을 시작. 못 찾으면 대기 후 재시도(예: 10초 간격). FC 전원이 라즈베리파이보다 늦게 들어오는 경우를 고려 |
| `drone.target` | 드론 모드 묶음 |
| `drone-mavlink-router.service` | `drone.target`에 속함. `~/drone/config/mavlink-router.conf` 사용. 죽으면 자동 재시작 |
| `drone-linkmon.service` | `drone.target`에 속함. 라우터를 거쳐 heartbeat를 계속 확인하고 끊김·복구를 `~/drone/logs/`와 journal에 기록. **읽기 전용**, 명령 안 보냄 |

- `drone-detect`가 시리얼 포트를 잡고 있으면 라우터와 충돌한다. 감지가 끝나면 포트를 확실히 놓고 나서 `drone.target`을 시작한다
- FC 연결이 끊기면(heartbeat 일정 시간 없음) `drone.target`을 내리고 감지 상태로 돌아간다
- 감지 결과를 `~/drone/state/mode`에 `drone` / `none`으로 남긴다. 나중에 가시화나 서버가 읽을 수 있게
- Go1 감지 로직은 이번에 만들지 않는다. Go1은 기존 자동 실행을 그대로 쓴다. 드론 쪽이 Go1 쪽과 자원(포트, 장치, clientId)을 겹쳐 쓰지 않는 것으로 공존시킨다

`~/drone/config/mavlink-router.conf`:
```ini
[General]
TcpServerPort = 5760

[UartEndpoint fc]
Device = /dev/serial0
Baud = 921600

[UdpEndpoint local_ctrl]   # 라즈베리파이 안의 제어 코드(MAVSDK)
Mode = Normal
Address = 127.0.0.1
Port = 14540
```

### 5단계. 지상국 연결 — Tailscale

Go1 때와 똑같이 Tailscale로 지상국과 연결한다.

- **Tailscale 설정은 바꾸지 않는다.** `tailscale up`을 다른 옵션으로 다시 실행하면 기존 설정이 초기화될 수 있으니 금지. 인증이 풀려 있거나 설정 변경이 필요하면 멈추고 보고한다
- 지상국 QGroundControl은 **TCP로 라즈베리파이의 Tailscale 주소 5760번**에 붙는다. 지상국 IP를 라즈베리파이 설정에 적을 필요가 없어서 이 방식을 기본으로 한다
- 지상국 IP로 UDP를 밀어 줘야 하는 경우만 `[UdpEndpoint gcs]`를 추가하고, 주소는 지상국의 Tailscale IP(100.x)를 쓴다
- 방화벽(ufw, nftables)이 켜져 있으면 `tailscale0` 인터페이스에서 5760이 열려 있는지 확인. 규칙 추가가 필요하면 승인 후, Tailscale 인터페이스에만 연다
- MQTT는 Go1이 쓰는 브로커를 같이 쓴다. 0-2에서 찾은 주소를 `~/drone/config/drone.env`에 기록만 해 두고 이번엔 연결하지 않는다

확인: 지상국 PC에서 `tailscale ping <라즈베리파이 이름>`, QGC에서 TCP `<라즈베리파이 Tailscale IP>:5760` 연결. 이 두 가지는 사용자에게 요청한다.

### 6단계. 제어 스크립트 준비 (작성만, 실행 금지)
`~/drone/scripts/`에 MAVSDK-Python으로 작성한다. 연결 주소 기본값은 `udpin://0.0.0.0:14540`이고 인자로 바꿀 수 있게 한다. 설치된 MAVSDK가 이 형식을 모르면 `udp://:14540`으로 맞춘다.
- `telemetry_watch.py`: 연결, 위치, 고도, 자세, 배터리, 비행 모드, arm 상태를 1Hz로 출력. 명령 없음. **이것만 실행해서 확인해도 된다**
- `arm_disarm_test.py`: arm → 3초 → disarm. 실행 전에 "프로펠러를 제거했습니까? (yes 입력)" 확인
- `takeoff_land.py`: 이륙 고도 1.5m → takeoff → 8초 → land. 위치 추정이 정상일 때만 진행하고 실행 전 확인 입력

각 파일 맨 위에 용도, 실행 조건, 위험도를 주석으로 적는다.

### 7단계. 재부팅 검증 (승인 후)
세 경우를 순서대로 확인한다. 각 경우마다 사용자에게 하드웨어 상태를 맞춰 달라고 요청한다.

| 경우 | 기대 결과 |
|---|---|
| FC 연결, Go1 없음 | `drone.target` 활성, `mode = drone`, 지상국 QGC가 Tailscale로 접속 |
| FC 없음 | `drone-detect`만 대기, `mode = none`, 에러 반복 없음 |
| Go1 연결 (FC는 있든 없든) | **Go1 세팅이 기준 스냅샷과 똑같이 동작** |

그리고 기준 스냅샷과 비교한다.
- Go1 코드 해시: 달라진 파일 0개여야 함
- Go1 서비스 상태: 동일
- enabled 유닛 목록: `drone-` 유닛 추가 외 변화 없음
- 포트: 드론 포트 추가 외 변화 없음
