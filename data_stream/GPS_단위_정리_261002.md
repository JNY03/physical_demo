# FC 위치·자세 데이터 단위 정리 — 객체 GPS 좌표 추정용

작성일: 2026-10-02
목적: 카메라 객체 탐지 결과에 드론의 GPS를 결합해 **탐지 객체의 GPS 좌표**를 계산할 때, 입력값의 단위를 하나로 맞추기 위함.

---

## 1. 결론 (먼저)

**어느 층에서 값을 받느냐에 따라 단위가 다르다.** 그대로 섞어 쓰면 10⁷배, 1000배 오차가 난다.

| 받는 곳 | 위도·경도 | 고도 | 자세(roll/pitch/yaw) |
|---|---|---|---|
| **MAVLink 원본** (pymavlink, `GLOBAL_POSITION_INT`·`GPS_RAW_INT`) | **정수, 도 × 10⁷** (`degE7`) | **정수, mm** | `ATTITUDE`: **rad** |
| **MAVSDK** (`telemetry.position()`) | 실수, **도** | 실수, **m** | `attitude_euler()`: **도** |
| **우리 브리지 MQTT 계약** ([CONTRACT_x500.md](../drone/CONTRACT_x500.md)) | 실수, **도 (WGS84)** | 실수, **m** | 실수, **도** (소수 2자리) |

**권장 통일 단위 (탐지 파이프라인 내부)**

| 항목 | 단위 | 타입 |
|---|---|---|
| 위도·경도 | **도 (WGS84 십진수)** | **float64 필수** (§4) |
| 고도 | **m** | float |
| 지상 오프셋(드론→객체) | **m** (North/East) | float |
| 각도 | 저장·전송은 **도**, 삼각함수 계산 직전에만 **rad** 변환 | float |

→ 브리지 MQTT를 구독한다면 이미 이 단위로 온다. 원본 MAVLink를 직접 읽는 경우만 변환이 필요하다.

## 2. MAVLink 원본 필드 단위 (pymavlink로 직접 읽을 때)

### `GLOBAL_POSITION_INT` (EKF 융합 위치, 50Hz — 객체 좌표 계산엔 이걸 쓴다)

| 필드 | 원본 타입 | 단위 | 변환 |
|---|---|---|---|
| `lat`, `lon` | int32 | 도 × 10⁷ | `/ 1e7` → 도 |
| `alt` | int32 | mm, 해발(AMSL) | `/ 1000` → m |
| `relative_alt` | int32 | mm, **이륙(home) 지점 기준** | `/ 1000` → m |
| `vx`, `vy`, `vz` | int16 | cm/s (NED: 북·동·하) | `/ 100` → m/s |
| `hdg` | uint16 | 도 × 100 (0~35999), `65535` = 모름 | `/ 100` → 도 |
| `time_boot_ms` | uint32 | ms (FC 부팅 후) | 시간 동기화용 |

### `GPS_RAW_INT` (GPS 수신기 원시값, 10Hz — fix 판정용)

| 필드 | 단위 | 비고 |
|---|---|---|
| `lat`, `lon` | 도 × 10⁷ | fix 없으면 0,0 → **좌표가 아니라 데이터 없음** |
| `alt` | mm (MSL) | |
| `eph` | **HDOP × 100 (무단위)** | 미터가 아니다. `65535` = 모름 |
| `h_acc` | mm | 실제 수평 정확도(m)는 이 필드 (MAVLink2 확장) |
| `fix_type` | 0~6 | **2 미만이면 위치 사용 금지** |

> 참고: [fc_state.py:82](../drone/scripts/fc_state.py#L82) 와 계약서의 `eph_m` 은 `eph/100` 을 m 로 표기하고 있다. 엄밀히는 HDOP 값이라 오차 반경(m)으로 쓰면 안 된다. 객체 좌표의 오차 추정이 필요하면 `h_acc` 를 쓸 것.

### `ATTITUDE` (100Hz)

| 필드 | 단위 | 기준 |
|---|---|---|
| `roll`, `pitch`, `yaw` | **rad** | NED 기준. yaw 0 = 진북, 시계방향 + (−π ~ π) |
| `rollspeed` 등 | rad/s | |

## 3. 객체 GPS 좌표 계산 시 단위 흐름

```
[드론]  lat_d, lon_d (도) , h (m, relative_alt)       ← GLOBAL_POSITION_INT
        roll, pitch, yaw (rad)                       ← ATTITUDE
[카메라] 픽셀 (u, v) + 내부 파라미터(fx, fy, cx, cy: px) + 장착각
          │
          ▼  광선 방향 → 지면(평지 가정)과 교차
        dN, dE  (m, 드론 바로 아래 지점 기준 북·동 오프셋)
          │
          ▼  미터 → 도 변환 (WGS84 장반경 R = 6378137 m)
        lat_o = lat_d + (dN / R) · 180/π
        lon_o = lon_d + (dE / (R · cos(lat_d·π/180))) · 180/π
```

- 탐지 거리 수백 m 이내면 위의 평면 근사로 충분하다(오차 cm 수준). 더 정밀하게 하려면 `pymap3d` 의 `ned2geodetic` 을 쓴다.
- 참고 감각: 위도 1° ≈ 111 km, 위도 36°(대전) 부근 경도 1° ≈ 90 km, **10⁻⁷° ≈ 1.1 cm**.

## 4. 놓치기 쉬운 함정

1. **float32 금지.** 경도 127.xxxxxxx 는 유효숫자 10자리가 필요한데 float32 는 약 7자리다 → **수 m 오차**. numpy·torch 텐서에 좌표를 넣을 때 `dtype=float64` 를 명시할 것. (degE7 정수로 유지하는 것도 방법)
2. **고도 기준.** `relative_alt` 는 *이륙 지점* 기준이지 *현재 발밑 지면* 기준이 아니다. 지형이 평평하다는 가정에서만 "지면 높이"로 쓸 수 있다. `alt`(해발)와 섞지 말 것.
3. **각도 단위 혼용.** 원본 MAVLink 는 rad, MAVSDK·브리지 계약은 도. `math.cos()` 에 도를 넣는 실수가 가장 흔하다.
4. **좌표계.** FC 는 NED(북·동·아래, z 가 아래로 +). OpenCV 카메라 좌표계(x 오른쪽, y 아래, z 전방)와 다르므로 회전 행렬 구성 시 축 매핑을 명확히 한다.
5. **fix 없는 0,0.** `fix_type < 2` 이면 좌표 계산을 하지 말고 결과도 `null` 로 낸다 (계약서와 같은 규칙).
6. **시간 정렬.** 프레임 촬영 시각과 위치·자세 샘플 시각이 어긋나면 yaw 10°/s 에서도 수십 px 가 틀어진다 ([alignment.py:19](../drone_rpi/alignment.py#L19) 참조). 위치(50Hz)·자세(100Hz) 를 프레임 시각에 맞춰 보간해서 쓴다.

## 5. 출력 형식 권장 (탐지 객체)

브리지 계약과 같은 단위를 쓰면 웹·서버 쪽에서 변환 없이 바로 지도에 찍을 수 있다.

```json
{
  "class": "person",
  "confidence": 0.87,
  "lat": 36.3500123,
  "lon": 127.3000456,
  "alt_m": null,
  "est_error_m": 3.2,
  "observed_at": 1759385412.123
}
```

- `lat`/`lon`: 도(WGS84), 소수 7자리 (≈1 cm 해상도, 실제 정확도는 GPS·자세 오차로 m 단위)
- 거리 계열: 전부 m
- 시간: epoch 초(float)

## 6. 다른 쪽(가시화·탐지)이 받는 GPS 단위

### 6-1. 가시화(웹)·백엔드 — MQTT `state` 채널

FC 원본을 직접 읽지 않고 **pi3 브리지가 변환해서 발행하는 MQTT** 를 받는다.
토픽 `zoneA/drone/x500-001/state` (구독은 `zoneA/+/+/state`), **1Hz** + 사건 시 즉시, QoS 1.
근거: [CONTRACT_x500.md §7-1, §13-3](../drone/CONTRACT_x500.md)

| 객체.키 | 단위 | 비고 |
|---|---|---|
| `gps.lat`, `gps.lon` | **도 (WGS84, 실수)** | `fix_type < 2` 면 `null` |
| `gps.fix_type` / `gps.fix` | 0~6 / 문자열 | |
| `gps.satellites` | 개수 | |
| `gps.eph_m` | 계약상 m (실제는 HDOP — §2 참고) | `null` = 모름 |
| `altitude.relative_m` | **m**, 이륙 지점 기준 | |
| `altitude.amsl_m` | **m**, 해발 | |
| `attitude.roll_deg` / `pitch_deg` / `yaw_deg` | **도** (소수 2자리) | 1초 넘게 끊기면 객체째 `null` |
| `*.age_s` | 초 | 값이 얼마나 낡았는지 |
| `timestamp` (공통 헤더) | ISO 8601, `+09:00` | 예 `2026-09-21T21:06:50.795+09:00` |

→ 가시화 쪽은 **변환 없이 그대로 지도에 찍으면 된다** (Leaflet·Kakao·Google 모두 십진 도 사용).

### 6-2. 탐지(drone_rpi) — 현재는 GPS를 받지 않는다

- [drone_rpi/](../drone_rpi/) 는 MQTT 나 FC 를 구독하지 않는다. GPS·자세 입력이 없다.
- 출력 좌표는 **영상 픽셀 좌표뿐**이고, 전역(GPS) 변환은 **백엔드 몫**으로 설계돼 있다
  ([records.py](../drone_rpi/records.py) 첫머리: "좌표는 로컬 영상 좌표뿐이다. 전역 변환은 백엔드 몫이다(AI-C-02)").
- 따라서 객체 GPS 를 계산하려면 둘 중 하나:
  1. **백엔드에서 계산** — 탐지 결과(픽셀 + `observed_at`) 와 MQTT `state`(도·m·도) 를 시각으로 맞춰 결합. 현재 설계와 일치.
  2. **drone_rpi 에서 계산** — drone_rpi 가 MQTT `state` 를 추가로 구독. 설계(AI-C-02) 변경이 필요.

  어느 쪽이든 입력 단위는 6-1 표 그대로(도·m·도)이고, §1 의 권장 단위와 같다.

### 6-3. 객체 좌표 계산에 MQTT `state` 를 쓸 때의 한계

| 문제 | 영향 | 대응 |
|---|---|---|
| **1Hz** 다 (원본은 위치 50Hz, 자세 100Hz) | 5 m/s 비행이면 샘플 사이 최대 5 m, yaw 변화 시 지면 투영이 크게 틀어짐 | 정밀도가 필요하면 브리지에 고주기 `pose` 채널 추가(예: 10Hz)를 요청하거나, 앞뒤 샘플 보간 + `age_s` 로 신뢰도 표시 |
| 시각이 ISO 문자열, 탐지 `observed_at` 은 epoch 초 | 비교 전 변환 필요 | 내부에선 epoch 초(float)로 통일 |
| `yaw_deg` 범위(−180~180 인지 0~360 인지)가 계약서에 명시 안 됨 | 각도 차/보간 시 360° 경계 오류 | 계산 전에 `% 360` 정규화. 브리지 담당과 계약서에 명시 합의 |
| `lat`/`lon` 반올림 자릿수가 계약서에 없음 | 소수 5자리 이하로 자르면 ≥1 m 오차 | 소수 7자리 이상 유지하도록 계약서에 명시 합의 |
| **FC 연결 상태로 값이 채워진 MQTT 를 아직 본 적 없다** ([CONTRACT §9](../drone/CONTRACT_x500.md)) | 위 단위는 계약·코드 기준이고 실측 미확인 | 기체 연결 후 `mosquitto_sub -t 'zoneA/+/+/state'` 로 실제 값·자릿수 확인 |

> 브리지 소스(`~/hw/pi/drone/drone_link.py`, `drone_node.py`)는 Pi 에만 있고 이 저장소에는 없어서, 반올림 자릿수·yaw 범위는 코드로 확인하지 못했다.
